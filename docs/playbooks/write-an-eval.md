# Écrire une évaluation

Référence : `docs/conventions/testing.md`, `evals/README.md`.

1. **Choisis le dossier** : `evals/scenarios/` (comportement attendu), `evals/adversarial/` (le fan essaie de casser : injection, « t'es un bot ? », demande de rencontre, mineur, détresse, paiement hors plateforme), `evals/regression/` (un bug réel, rejoué pour qu'il ne revienne pas, avec le numéro de la fiche de tâche).
2. **Fichier** : `<slug>.yaml`, au format strict de `apps/api/src/scripts/evals/scenario.ts` (une clé inconnue, un risque ou une intention hors liste, une regex cassée font échouer `pnpm test`) : `description`, `persona_version: demo`, `tier` (`smoke` par défaut, `full` pour ne tourner qu'avec `--full`), `fan_facts` (fictifs), `situation` (depuis combien d'heures elle le connaît, ce qu'il a dépensé, heure locale, âge confirmé, dernière offre, manque d'argent avoué, ventes gelées), `history` (messages précédents, fictifs), `inbound` (son message, ou une liste s'il en a envoyé plusieurs), `alerts` (ses alertes écrites en phrase, chacune avec un `name` du scénario, données au cerveau comme sur un vrai message), `expect` :
   - `brief` : contraintes sur la sortie du cerveau (`intent_in`, `risks_contain`, `risks_absent`, `action_in`, `desire_signals_contain`, `alerts_seen` : exactement les alertes que le cerveau doit voir, par leur `name`, `[]` pour aucune).
   - `decision` : ce que décide le code (`handoff` : un humain reprend ; `offer` : le cerveau propose et `offerDecision` l'autorise).
   - `voice` : assertions sur le texte (`must_not_match`, `must_match_any`, `bubbles_min`, `bubbles_max`) et `judge` : minima par critère pour ce scénario. Une garde dure bloquante fait toujours échouer.
   - `then` (facultatif) : la suite de la conversation, rejouée sur le même chemin sans clavier ni envoi. Chaque tour donne `after_minutes` (le temps écoulé depuis sa réponse, 2 par défaut ; 600 pour le lendemain), `event: buys_step` s'il a acheté entre-temps la dernière étape payante envoyée (comme l'historique de Reveal le dirait), son `inbound` et l'`expect` de sa réponse. Ses bulles, son désir, sa disponibilité et son déroulé de script passent d'un tour au suivant comme la base les garderait. Le juge note chaque réponse ; une conversation vaut sa réponse la plus faible. Un humain qui prend la main arrête la conversation. Chaque tour coûte comme un scénario : une conversation longue prend `tier: full`.
3. **Données** : jamais un vrai fan, jamais un vrai message. Noms et faits inventés. Un scénario qui a besoin d'un vrai cas est anonymisé d'abord (noms, lieux, dates décalées).
4. **Lance** : `pnpm evals -- --file evals/<dossier>/<slug>.yaml`. Vérifie que le scénario échoue sur la version qui a le bug (régression) ou passe sur la version courante (scénario). Chaque conversation est écrite en entier dans `.scratch/evals/<date>/` (ignoré par git, ou le dossier de `--transcripts`) ; avec sa vraie fiche (`--persona-from-crm`), la console n'affiche que les notes et les fautes, jamais ses mots. `--cap-eur` fixe le plafond de la passe (6 € par défaut, 25 € au plus) : une passe payante se demande d'abord à Charles, nombre de conversations et coût annoncés.
5. **Seuils** : `evals/thresholds.json` fixe les minima par critère pour `smoke` (CI) et `full` (manuel). N'abaisse jamais un seuil pour faire passer la CI ; ouvre une fiche de tâche.
6. **Garde de la qualité** : chaque nuit, la CI lance l'e2e (job `nightly`). `pnpm probe` puis `pnpm evals` (job `evals`) tournent chaque dimanche soir et après chaque fusion sur `main` qui touche l'IA (`packages/llm`, les modules `agent` et `persona`, `personas/`, `evals/`) : environ 3 € par passage, choix de Charles du 21/11. Sans le secret `LLM_XAI_API_KEY`, les évaluations sont sautées : le résumé du run l'écrit (« Évaluations sautées, clé absente ») avec un avertissement, et le run reste vert (« nightly vert », décision de Charles du 06/11). Avec la clé, les deux échouent si rien n'est mesuré, et `pnpm evals` échoue tant que la suite compte moins de `min_scenarios` fichiers YAML. Une évaluation qui échoue rend donc le run rouge. `pnpm check` refuse trois choses : qu'on retire ces deux lignes du job `evals`, qu'on les saute pour une autre raison que l'absence de clé, ou qu'on y mette `continue-on-error`. Le juge note chaque réponse écrite sur les neuf critères ; un critère que personne n'a pu noter fait échouer la suite.
7. **Coût** : un scénario = 2 à 3 appels LLM (cerveau, voix, juge). `smoke` reste à 30 scénarios au plus : les autres prennent `tier: full`.
8. **PR** : le rapport de `pnpm evals` (réponses, notes, moyennes) est collé dans la description.

Sur le PC du propriétaire, la clé n'est jamais dans un fichier (ADR 0016) : `pnpm evals --key-from-crm` lit celle qu'il a collée dans Réglages › Modèles IA, par la base en lecture seule (`DATABASE_ADMIN_URL`, `CREDENTIALS_ENCRYPTION_KEYS`), la garde en mémoire et n'en affiche que le nom du service.
