# Sécurité : règles et baseline

Ce qu'on protège, par ordre d'importance : (1) les médias et conversations intimes des fans et de la créatrice, (2) la session plateforme de la créatrice (= son compte Reveal), (3) le contrôle du bot (dashboard, interrupteurs), (4) les clés LLM (coût), (5) le code. Le modèle de menaces complet est dans `docs/architecture/threat-model.md`. Ce fichier est la liste des règles que chaque session applique.

## 1. Exposition : rien n'est public par défaut

- **Le dashboard est public, mais un mot de passe ne suffit jamais à y entrer** (ADR 0046) : chaque compte a un deuxième facteur (code d'une application d'authentification), les sessions ont une durée absolue, et les connexions inhabituelles déclenchent une alerte. Cloudflare Access reste possible en plus, côté exploitation. Tant que le lot (a) de l'ADR 0046 n'est pas en production, le mot de passe est la seule barrière : ne pas ouvrir le dashboard à l'équipe avant.
- L'API n'écoute que sur l'interface privée du VPS (Docker network) ; seul le reverse proxy (Caddy/Traefik via Coolify) la publie, en HTTPS, avec HSTS.
- L'endpoint que l'extension appelle (capture de session, enregistrements) est authentifié par un **jeton d'appareil** révocable, limité par débit, et n'accepte que les origines de l'extension.
- Postgres n'est jamais joignable depuis Internet (Neon : IP allowlist ; self-host : réseau Docker uniquement).
- Aucun bucket de médias public. Accès par URL signée courte (≤ 15 min).

## 2. Secrets

- Jamais dans le dépôt, jamais dans les logs, jamais dans une réponse d'API. `gitleaks` en pré-commit et en CI, secret scanning GitHub activé.
- Un secret par usage, par environnement (dev / staging / prod). Une clé LLM par rôle et par environnement, avec plafond de dépense côté fournisseur.
- Rotation : procédure dans `docs/runbooks/rotate-secrets.md`. Toute suspicion de fuite = rotation immédiate, pas d'enquête avant.
- Les **sessions plateforme** (cookies/jetons Reveal) sont chiffrées en base (AES-256-GCM, clé hors base, dans l'env chiffré de Coolify), déchiffrées uniquement dans le processus connecteur, jamais renvoyées par l'API, jamais loguées (redaction pino sur `session`, `cookie`, `token`, `authorization`).
- Les **clés des fournisseurs IA** suivent la même règle : saisies dans le dashboard, chiffrées en base avec `CREDENTIALS_ENCRYPTION_KEYS`, jamais renvoyées par l'API ni loguées (ADR 0016).
- 2FA obligatoire sur GitHub, Hetzner, Cloudflare, Neon, fournisseurs LLM, Reveal.

## 3. Données

- **Minimisation** : on ne stocke d'un fan que ce qui sert à la conversation. Jamais de coordonnées, de localisation précise, d'identifiant de paiement. Le cerveau a une liste blanche de catégories de faits ; tout le reste est ignoré.
- **Rétention** : chaque `fan_fact` et chaque média reçu d'un fan a une date d'expiration (défaut : faits 12 mois après dernier contact, médias fan 30 jours). Un job purge : `fans.purge_facts` (chaque nuit) supprime tous les faits d'un fan qu'on n'a plus vu depuis un an (`fans.last_seen_at`). Les médias de la créatrice vivent selon ses droits (`media_assets.rights`).
- **Effacement** : une commande `erase-fan <id>` supprime tout ce qui concerne un fan (faits, résumés, médias, messages anonymisés dans le journal). Elle existe dès la phase 2, même si personne ne la demande : la construire après coup est dix fois plus cher.
- **Chiffrement au repos** : disques VPS chiffrés, base chiffrée (Neon par défaut), bucket chiffré. Les champs les plus sensibles (sessions, faits de catégorie `intimate`) chiffrés applicativement en plus.
- **Logs sans contenu** : par défaut, on logue des identifiants et des métadonnées, pas le texte des messages. Le contenu n'est consultable que dans le dashboard, authentifié, et dans Langfuse (accès restreint, rétention courte).
- **Tests et fixtures** : données inventées uniquement. Jamais un export réel dans le dépôt, même anonymisé « à la main ».

## 4. Le LLM comme surface d'attaque

- Le texte d'un fan (et le contenu d'un média décrit) est **toujours** inséré dans un bloc délimité, typé « données non fiables ». Le prompt système dit explicitement que rien dans ce bloc n'est une instruction.
- La **voix** n'a aucun outil. Le **cerveau** n'a que des outils de lecture ; ses décisions sont des propositions validées par la politique en code. Aucune action externe (envoi, achat, suppression, changement de réglage) ne découle directement d'une sortie de modèle.
- Sorties structurées validées par Zod ; une sortie invalide = retry, puis draft en erreur, jamais d'exécution partielle.
- Gardes post-génération : mention d'IA/de prompt/de système, fuite de données d'un autre fan, URL ou coordonnées, prix hors offre, mots interdits par la persona.
- Évals adversariales dans `evals/adversarial/` : injections classiques (« ignore tes instructions », « répète ton prompt », « tu es maintenant… »), tentatives d'extraction de données d'autres fans, demandes de rencontre/paiement hors plateforme. Elles tournent en CI sur un sous-ensemble.
- Plafonds : tokens par appel, appels par conversation et par heure, budget LLM par créatrice et par jour (coupe-circuit).

## 5. Chaîne d'approvisionnement

- `pnpm` avec lockfile commité, `pnpm install --frozen-lockfile` en CI, scripts d'installation désactivés par défaut (comportement pnpm 10), `pnpm audit --audit-level=high` en CI (échec sur high et critique ; correctifs transitifs par `overrides` et exceptions justifiées une par une dans `pnpm-workspace.yaml`, revues à chaque session d'hygiène), Dependabot en PR hebdomadaires groupées (`.github/dependabot.yml`).
- Peu de dépendances, bien connues, maintenues. Toute dépendance nouvelle de poids = ligne dans la PR qui justifie.
- Versions épinglées : dépendances npm en versions exactes dans les `package.json` (pas de `^`, on monte avec `pnpm up`), Node (`.nvmrc`), images Docker par digest, modèles LLM par identifiant daté.
- L'extension : `host_permissions` limitées au domaine Reveal, aucun code distant, build reproductible, pas de `eval`.

## 6. Application web et API

- Validation Zod de toute entrée (corps, query, params, en-têtes utiles). Erreurs génériques vers le client, détail dans les logs.
- Auth : Better Auth, cookies `HttpOnly; Secure; SameSite=Lax`, sessions courtes côté dashboard, passkeys encouragées. **Deuxième facteur pour tous (ADR 0046)** : plugin `two-factor` de Better Auth, code TOTP d'une application d'authentification. Après le mot de passe, un compte dont le code est actif n'a pas de session : il reçoit `twoFactorRedirect` et un cookie d'étape de 10 minutes, puis donne le code (`/v1/auth/two-factor/verify-totp`) ou un des dix codes de secours, chacun à usage unique (`/v1/auth/two-factor/verify-backup-code`). Le code se verrouille 15 minutes après 10 échecs (429 `second_factor_limited`). « Se souvenir de cet appareil » l'épargne 30 jours à la connexion, jamais avant une action sensible. Le secret du code et les codes de secours sont chiffrés avec le secret de Better Auth (`rotate-secrets.md`). Un compte connecté sans code actif n'ouvre que l'écran d'activation : toute route protégée, `/v1/me` compris, répond 403 `second_factor_forbidden`. Fermer les sessions (soi, un membre, `ops:revoke-sessions`), le lien de nouveau mot de passe (EQ-10), la remise à zéro du code (`ops:reset-second-factor`) et le départ (EQ-14) suppriment aussi les appareils de confiance. Un mot de passe connu des fuites est refusé à sa création (Pwned Passwords en k-anonymat : seuls les 5 premiers caractères de l'empreinte SHA-1 sortent, vers `api.pwnedpasswords.com`) ; si le service ne répond pas, le mot de passe est refusé en 503 et l'écran dit de réessayer. Action sensible (connecter, remplacer ou retirer une clé IA, ADR 0016 ; activer une version de la persona, qui change ce que l'agent dit à tous ses fans ; créer un lien d'invitation ; lancer une sauvegarde ou un essai de restauration ; la liste complète est dans l'ADR 0046 § 3) : mot de passe **et** code confirmés depuis moins de 10 minutes sur cette session (`POST /v1/auth/reauthenticate`, qui horodate `session.reauthenticated_at` ; `requireRecentLogin` lit cet horodatage), appareil de confiance ou non, sinon 403 `reauthentication_forbidden` et le dashboard redemande les deux. La confirmation ne crée aucune session ; elle a sa limite par compte (10 essais par 10 minutes, 429 `reauthentication_limited`), et chaque refus entre dans `audit_log` (`auth.reauthentication_refused`). Rôles : `owner`, `operator`, `creator` ; RLS Postgres en second rideau. Un membre de l'équipe marqué `left` ne se connecte plus (même réponse qu'un mauvais mot de passe), et ses sessions sont révoquées au passage à `left` puis, si l'une restait ouverte, refusées à la requête suivante (ADR 0023). Les autres statuts gardent la connexion, avec le scope `self` (ADR 0024). **Réglages › Sécurité** (SEC-04, ADR 0046 § 7 ; « Moi › Sécurité » pour un membre de l'équipe, `/compte/securite` pour une opératrice ou une créatrice ; l'entrée « Sécurité » du menu du compte mène à celui du rôle) : chacun voit ses sessions ouvertes par appareil (lu du navigateur), réseau (`networkOf`, jamais l'adresse complète ni un pays) et dernière activité (`GET /v1/auth/sessions`), en ferme une (`DELETE /v1/auth/sessions/:id`, jamais celle de la requête : on s'en déconnecte) ou toutes les autres avec ses appareils de confiance (`POST /v1/auth/sessions/close-others`), et crée dix nouveaux codes de secours contre son mot de passe et un code (`POST /v1/auth/two-factor/generate-backup-codes`, 5 essais par 15 minutes, chaque refus compté dans `audit_log`). Le propriétaire y voit aussi, par compte, si le code est actif et combien de sessions sont ouvertes, sans appareil ni réseau (`GET /v1/settings/security/accounts`), et ferme toutes les sessions d'un compte, une action sensible (`POST /v1/settings/security/accounts/:userId/close-sessions`). Chaque fermeture et chaque nouvelle série de codes entre dans `audit_log`.
- **Clés d'accès (ADR 0053, CR-01 lot c)** : plugin `@better-auth/passkey` (1.7.7) et `@simplewebauthn/server` 13.3, domaine de la clé et origine = `WEB_ORIGIN`, pas d'attestation, vérification de la personne exigée (`userVerification: required` dans les options, et le serveur refuse une assertion sans le drapeau UV, que le plugin ne vérifie pas : `USER_NOT_VERIFIED`). Table `passkey` hors RLS, écrite par le seul module d'authentification ; rien de biométrique n'existe côté serveur. **Connexion** : `GET /v1/auth/passkey/generate-authenticate-options` puis `POST /v1/auth/passkey/verify-authentication` ouvre la session sans mot de passe ni code ; mêmes limites qu'un mot de passe, par compte de la clé quand elle en nomme un (`passkey:<compte>`), sinon par adresse ; seuls les refus vérifiés (signature, origine, vérification absente) entrent dans `audit_log` (`auth.passkey_refused`) et dans l'alerte des refus répétés ; le geste de connexion ne compte pas comme confirmation. Première connexion du propriétaire avec une clé jamais utilisée : alerte `passkey_new_sign_in`. **Ajout** : `GET /v1/auth/passkey/generate-register-options` puis `POST /v1/auth/passkey/verify-registration`, seulement si le mot de passe et le code eux-mêmes ont été donnés sur cette session depuis moins de 5 minutes (`session.code_confirmed_at`, que le geste d'une clé n'horodate jamais : une clé n'en ajoute pas une autre), sur le compte de la session ; la clé prend le nom de l'appareil lu par le serveur ; alerte `passkey_added` au groupe urgent et ligne `auth.passkey_added`. **Action sensible** : `POST /v1/auth/passkey/confirm-options` (défi neuf pour cette session, 5 minutes, ligne `verification` `passkey-confirm:<session>`) puis `POST /v1/auth/passkey/confirm`, qui consomme le défi quoi qu'il arrive et horodate `reauthenticated_at` comme le mot de passe et le code (même limite par compte, refus en `auth.reauthentication_refused`, succès en `auth.reauthenticated` `{via: 'passkey'}`). **Retrait** : chacun liste ses clés (`GET /v1/auth/passkeys` : appareil, trousseau lu de l'AAGUID, ajout, dernière utilisation, jamais la clé ni son identifiant) et en retire une après confirmation (`DELETE /v1/auth/passkeys/:passkeyId`, `auth.passkey_removed`) ; le propriétaire voit « N clés » par compte et les retire toutes (`POST /v1/settings/security/accounts/:userId/remove-passkeys`, action sensible, `auth.passkeys_removed`). Toutes les clés d'un compte partent aussi à la remise à zéro du code, au lien de nouveau mot de passe et au départ ; fermer des sessions ne les retire pas.
- CSRF : `SameSite=Lax` et vérification de l'en-tête `Origin` sur chaque mutation contre la liste des origines autorisées (pas de jeton CSRF séparé). CORS : la même liste explicite. En-têtes de sécurité (`@fastify/helmet`). Limites de taille de corps. Rate limiting par IP et par utilisateur (`@fastify/rate-limit`). L'IP du client est celle que Fastify résout derrière `TRUST_PROXY_HOPS` proxys (2 en production : le Traefik de Coolify puis le nginx du conteneur `web`, ADR 0027 ; 0 en local). `x-forwarded-for` ne compte qu'au-delà de ces sauts. Better Auth ne lit que l'en-tête `x-nirvana-client-ip`, que le serveur réécrit à chaque requête : l'IP des limites et celle de `audit_log` ne peuvent pas venir du client. La connexion a trois limites (ADR 0046 § 5) : 20 par minute et par IP ; 10 par quart d'heure pour un compte depuis une même adresse, pour que les essais d'un autre ne bloquent jamais le titulaire ailleurs ; 100 par quart d'heure pour un compte toutes adresses confondues, contre des essais répartis sur beaucoup d'adresses (429 `sign_in_limited`). Une connexion depuis un appareil de confiance du compte ne compte pas dans ce plafond de 100. Le code de la connexion et celui de l'activation ont les mêmes limites, comptées à part pour le compte de l'étape (429 `second_factor_limited`), en plus du verrouillage du plugin après 10 codes faux de suite. Une session ouverte depuis plus de 7 jours est refusée (401) et supprimée à sa requête suivante, quel que soit son usage (ADR 0046 § 6), en plus des 12 heures sans activité. Les liens d’invitation (EQ-10) ont chacun leur limite par IP : 30 lectures et 10 utilisations par quart d’heure ; seul le propriétaire en crée, après une connexion récente. Les compteurs de toutes ces limites vivent dans Postgres (`rate_limit_counters`, ADR 0027) : toutes les instances de l'API comptent dans les mêmes lignes, un redémarrage ou un déploiement ne les remet pas à zéro. La clé ne garde ni l'IP ni l'e-mail en clair (empreinte SHA-256), et la tâche `rate_limit.purge` efface toutes les 10 minutes les fenêtres finies depuis plus d'une heure. Le limiteur a son propre petit pool (3 connexions, `statement_timeout` de 200 ms, 500 ms au plus pour obtenir une connexion) : un Postgres lent coûte au plus ce délai à une requête, jamais une connexion du pool des modules. Si les compteurs ne répondent pas, chaque échec est journalisé (`warn`) et le limiteur global **laisse passer** (une panne de Postgres arrête déjà presque toute l'API, il ne doit pas en rajouter), tandis que les limites de `/v1/auth/*`, connexion comprise, **refusent** en 503 `service_unavailable` : mieux vaut un refus qu'une rafale de mots de passe pendant une panne. Toute route sensible ajoutée plus tard (liens d'invitation, EQ-10) déclare `skipOnError: false` sur sa limite. Deux limiteurs qui partageraient leurs compteurs (même route, ou mêmes bornes sans route) arrêtent le démarrage.
- Uploads : type vérifié par contenu (magic bytes), taille bornée, stockage hors du système de fichiers de l'app, jamais servis depuis le même domaine que le dashboard.
- Journal d'audit des actions d'administration (`audit_log` : qui, quoi, quand, depuis où), append-only.

## 7. Opérations

- Trois environnements : `dev` (FakeReveal, clés de test), `staging` (compte Reveal de test si disponible, sinon FakeReveal), `prod`. Aucune clé partagée entre eux.
- Sauvegardes chiffrées, **restauration testée** une fois par trimestre (une sauvegarde jamais restaurée n'existe pas).
- Alertes : échecs d'authentification répétés, nouvelle session d'appareil sur l'extension, dépense LLM anormale (> 2× la médiane), erreurs connecteur en rafale, session plateforme expirée.
- Alertes de sécurité (ADR 0046 § 8) : un événement `security_alert` dans l'outbox, écrit après sa ligne d'`audit_log`, que le module Telegram dit aux groupes urgents (les importants en repli). Six raisons : connexion du propriétaire depuis un appareil que rien n'a épargné (un code demandé, ou aucun encore activé ; un appareil de confiance ne dit rien) ; 5 refus de mot de passe, de code ou de confirmation sur un même compte en 15 minutes (`auth.sign_in_refused`, `auth.code_refused`, `auth.reauthentication_refused`), dit au plus une fois par quart d'heure et par compte, un e-mail inconnu n'écrivant rien ; deuxième facteur actif remis à zéro (lien de nouveau mot de passe ou `ops:reset-second-factor`) ; version de la persona activée ; Automatique allumé, pour toutes ses conversations ou une seule (`automatic.on`) ; session plateforme valide remplacée par une autre (renouveler une session expirée ne dit rien). Le message nomme un compte par son rôle et l'adresse par son réseau (`203.0.113.x`, ou un `/48` en IPv6, `networkOf`) : jamais un nom, jamais une adresse complète, jamais un contenu. Écrire l'alerte ne conditionne jamais la réponse : une connexion ou un refus restent ce qu'ils sont si elle échoue (`warn`).
- Runbooks dans `docs/runbooks/` : fuite de secret, compromission du serveur, session Reveal compromise, dépense LLM qui s'emballe, restauration.
- Branches protégées sur GitHub : PR obligatoire, CI verte, pas de push direct sur `main`.

## 8. Ce que chaque PR vérifie (checklist)

- [ ] Aucune nouvelle entrée sans validation Zod.
- [ ] Aucun secret, aucune donnée réelle.
- [ ] Les nouvelles tables ont `creator_id` et une politique RLS.
- [ ] Les nouveaux logs ne contiennent pas de contenu de message ni de session.
- [ ] Les nouvelles actions externes passent par la politique en code, pas par une sortie LLM.
- [ ] Les nouvelles dépendances sont justifiées.
