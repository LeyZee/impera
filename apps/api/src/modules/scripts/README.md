# Module `scripts`

**Rôle.** Les scripts que la créatrice tourne carton par carton (ADR 0056). L'atelier des **structures** de l'agence, leurs versions, la **file de structures** de chaque créatrice et le rendu des **cartons** (SC-01) ; la **cadence** qui lui demande ses scripts (SC-02 lot a). Viendront le parcours de dépôt (SC-02 lot b), la nomenclature et l'export (SC-03).

**Peut dépendre de.** aucun module métier (feuille). Les limites de la persona lui viennent de `persona` par le composition root (`limitsOf`, sa version active) ; la demande de script est écrite par `content-drops`, branché de même (`requests`, son `scriptRequests`).

**Tables possédées.** `script_structures`, `script_structure_versions`, `script_structure_queue` (migrations 0084 et 0095) et `script_cadences` (migration 0121) ; `platform_scripts`, `platform_script_steps` et `platform_script_step_media` (migration 0206, les scripts natifs) ; `prepared_scripts` (migration 0229, les scripts en préparation ; migration 0230 : le rôle de service insère dans `platform_script_branches` pour la reconnaissance).

- La bibliothèque (`script_structures`, `script_structure_versions`) appartient à l'agence : hors RLS des créatrices, sous les politiques de l'équipe (`withMember`). Le propriétaire écrit, le propriétaire et les managers actifs lisent, personne d'autre (un chatteur, un compte de créatrice : rien).
- Une version porte le nom, le moment et les segments (`ScriptSegment[]`, relus par le contrat). La dernière version change sur place tant qu'elle n'est pas figée ; une fois figée (`frozen_at`, posée par `structures.freeze` quand une demande la prend, SC-02), un enregistrement écrit la version suivante (règle 6). Un déclencheur refuse toute modification d'une version figée, tout changement de numéro et toute suppression, pour tous les rôles.
- Une structure retirée est archivée (`archived_at`), jamais supprimée ; l'archivage la sort de toutes les files.
- La file (`script_structure_queue`) est par créatrice, sous sa RLS et les mêmes portées (`withTenantMember`) : un compte de la créatrice n'en lit rien. Elle se remplace en entier, sous un verrou par créatrice.

- La cadence (`script_cadences`) est par créatrice, sous sa RLS et les mêmes portées : le propriétaire règle `days` (1 à 90, 14 sans ligne), le propriétaire et les managers actifs lisent ; ce que le job a trouvé (`outcome`, `skipped`, `checked_at`) n'est écrit que par lui, en rôle admin.

**Cadence** (ADR 0056 § 2, `application/ask-scripts.ts`, job horaire `scripts.ask_scripts`). Pour chaque créatrice dont le prochain script tombe dans la semaine (`nextScriptDue`, son jour à elle ; le premier une semaine après le premier passage, chacun des suivants `days` après le précédent ; une cadence en pause repart d'aujourd'hui), `chooseStructure` prend la première structure de sa file qui ne touche aucune limite de sa persona active et nomme celles sautées. La version est figée, relue (une sauvegarde entre la lecture et le gel ne passe pas), demandée (`content_requests` origine `cadence`, `structure_version_id`, une par jour d'échéance), puis sort de la file. Sans persona active : rien (`no_persona`) ; toutes les structures bloquées : rien (`blocked`) ; file vide : la dernière structure redemandée (`reused`), ou rien (`queue_empty`). L'écran de l'agence met en ambre tout ce qui n'est pas `asked`. Rejouable : un passage coupé entre la demande et la file est rattrapé au suivant.

**Règles** (contrat `packages/contracts/src/scripts.ts`, partagé avec l'écran) : `scriptStructureFaults` (au moins une étape ; clés uniques ; une étape a un emplacement ; lettres de variantes uniques, trois au plus ; un pont relie par leurs clés l'étape juste avant lui et celle juste après, un seul pont entre deux étapes) et `scriptSegmentCodes` (numéros dérivés de l'ordre, `E<n>` et `P<n><m>`). Dans le domaine : `disgustBlocks` (une étape qui touche `never_do`, `never_show` ou `disgusts` de sa persona, un pont dont l'accroche touche `never_say` ou `disgusts`, en mots entiers, lu en code), `saveDecision` (règle 6), `queueView`.

**Routes** (montées sous `/v1`, codes d'erreur `SCRIPT_ERROR_CODES`) :

- `GET /script-structures`, `GET /script-structures/:structureId` : propriétaire et opérateurs (la RLS ne montre rien à un chatteur) ;
- `GET /script-structures/starters` : les structures de départ (`SCRIPT_STARTERS`, ADR 0064 § 4), données des contrats, les mêmes pour toute agence ; en dupliquer une, c'est un `POST` de son corps sous un nouvel identifiant ;
- `POST /script-structures` (propriétaire) : écrit la structure et sa version 1 sous l'identifiant du client (201) ; le même envoi rejoue (200) ; le même identifiant avec un autre contenu donne 409 `script_structure_conflict`. Une règle cassée donne 400 avec le message à la place du segment fautif ;
- `PUT /script-structures/:structureId` (propriétaire) : enregistre sur `basedOnVersion` ; 409 `script_structure_stale_conflict` si une autre version a été écrite depuis ; 400 `script_structure_creator_invalid` si la créatrice réservée n'existe pas ou si la structure est déjà dans la file d'une autre ;
- `DELETE /script-structures/:structureId` (propriétaire) : archive (204) ;
- `GET /creators/:creatorId/script-queue` (propriétaire, manager actif) : la file, chaque entrée avec ce qui la bloque aujourd'hui (`blocks`) ; `personaChecked` vaut `false` sans persona active ; tout autre compte reçoit 404 `script_queue_creator_not_found`, que la créatrice existe ou non (recette SEC-06) ;
- `PUT /creators/:creatorId/script-queue` (propriétaire) : remplace la file ; 422 `script_queue_structure_unprocessable` (inconnue, archivée, réservée à une autre) ou 422 `script_queue_disgust_unprocessable` avec, par structure, l'étape et l'entrée de sa persona qui bloquent.

- `GET /creators/:creatorId/script-cadence` (propriétaire, manager actif) et `PUT` (propriétaire, `{ days }`) : la cadence et ce que le job a trouvé la dernière fois (`lastDueOn`, `outcome`, `skipped`, `checkedAt`) ; 404 `script_cadence_creator_not_found` comme pour la file.

- `GET /script-structures/:structureId/cards/:segmentKey?format=card|folder|thumbnail&variant=A|B|C` : le carton d'un segment de la version courante, ou d'une de ses séries. `card` (défaut) rend le SVG pour l'application, `folder` un PNG de 1080 × 1080 pour le dossier, `thumbnail` un PNG de 320 × 320 pour les chatteurs. 404 `script_card_not_found` pour une clé ou une variante absente.
- `POST /script-structures/cards/preview` (propriétaire) : l'aperçu de l'atelier, le carton (`card`) ou la vignette (`thumbnail`) d'un segment d'un brouillon jamais enregistré, toujours en SVG avec les mêmes en-têtes (`no-store`, `default-src 'none'`) ; les segments sont relus un par un, pas contre les règles de structure, pour qu'un brouillon en cours se voie. 404 `script_card_not_found` pour une clé absente.

**Cartons** (`domain/cards.ts`, ADR 0056 § 3 et ADR 0064). Le dessin d'OnlyScript dans la typographie d’Impera : la **couleur du script** (trois tons, `color` de la version) en dégradé sur tout le carton, « ÉTAPE n » et le nom de l'étape au centre, l'intention entre guillemets avec « (GRATUIT) » ou « (PAYANT) » (`access` de l'étape), ce qu'il faut tourner, les indications (trois au moins quand il y en a), l'ambiance, et en pied une pastille par série. En haut, le moment et son icône au trait (soleil, lune, ou les deux pour un script qui passe partout). Une variante a son carton de série (« Série A », sa consigne, les pastilles des séries de l'étape, la sienne pleine) ; un pont dit « PONT n & m », son teaser, toujours « (GRATUIT) », sa photo teasing, et en pied les noms des deux étapes qu'il relie, jointes par une arche en pointillé. La vignette des chatteurs ne garde que l'étape, son nom, ce qu'il faut tourner et « (GRATUIT) » ou « (PAYANT) ». Le code choisit l'encre (claire ou foncée) qui se lit sur les trois tons et leurs mélanges, et le texte est écrit en encre pleine ; une couleur où aucune n'atteint 4,5:1 est refusée à l'enregistrement (`ReadableScriptColorSchema`). Fonction pure : les mêmes octets pour la même entrée. Le texte de l'agence est échappé ; le SVG ne nomme ni fichier, ni image, ni lien, et la route l'envoie avec `Content-Security-Policy: default-src 'none'`. Le PNG est tiré par librsvg (`infra/card-rasterizer.ts`, aucune dépendance npm) : `rsvg-convert` dans l'image Docker, où l'ffmpeg d'Alpine n'a pas de décodeur librsvg, sinon le décodeur librsvg d'ffmpeg (poste de dev et CI), choisi une fois par processus, avec une configuration de polices qui ne nomme que `infra/fonts/` (Geist et Instrument Serif en TTF, SIL OFL 1.1, licences à côté) : le même SVG donne le même PNG dans une même image Docker (une autre version de librsvg, pango ou freetype peut changer l'anticrénelage, on ne compare donc jamais un PNG d'une machine à l'autre). Deux rendus au plus tournent en même temps. L'image Docker copie ce dossier comme celui des factures, et sa construction échoue si `rsvg-convert` n'y tire pas un SVG.

**Scripts natifs** (ADR 0099 § 1 temps 2, fiche `PROPOSED-vault-import-scripts.md`, `application/import-platform-scripts.ts`, job `scripts.import_platform_scripts`, un compte à la fois). Aucune horloge : l'import est demandé avec chaque synchronisation du coffre que le propriétaire lance (`askImport`, branché par le composition root sur `connectors.onVaultSyncAsked`), mis en file sur la file du compte juste derrière `connector.vault_sync`, pour lire les liaisons fraîches ; une fusion ne lit donc jamais la plateforme toute seule. Les scripts de vente que la plateforme garde pour un compte (`listPlatformScripts` du connecteur : une séquence Reveal = un script, une étape seule = un script d'une étape) sont recopiés dans `platform_scripts`, leurs étapes dans l'ordre de la plateforme (`position` = `stepIndex`) dans `platform_script_steps`, et les médias de chaque étape (vendus et aperçus, dans leur ordre) dans `platform_script_step_media`, par l'identifiant de la plateforme. La plateforme est la source : Impera n'écrit aucun script ici.

- Le nom reste celui de la plateforme ; le prix est lu tel quel (centimes TTC, 0 pour une étape offerte), jamais recalculé.
- `planPlatformScripts` compare une empreinte (`platformScriptFingerprint` : nom, moment, chaque étape avec son texte, son prix et ses médias) : un script nouveau est ajouté ; un script changé, ou revenu après avoir disparu, est réécrit en entier et actif ; un script qui ne change pas ne bouge que par `synced_at` ; un script disparu est désactivé (`active = false`, `deactivated_at`), jamais supprimé, avec ses étapes, parce qu'un déroulé ou une récompense peut encore le nommer. Tout le plan d'un compte passe dans une transaction.
- Les bornes (`PLATFORM_SCRIPT_*_MAX` des contrats, tenues aussi par des CHECK en base), comme celles du coffre : un nom de script ou d'étape au-delà de 200 caractères et un texte d'étape au-delà de 4 000 sont coupés à l'import (`boundedPlatformScript`, jamais au milieu d'un emoji) ; un script de plus de 50 étapes, ou de plus de 50 médias vendus ou 50 aperçus dans une étape, ou dont un identifiant de la plateforme dépasse 200 caractères, n'est pas importé (compté dans `refused`), et un script déjà connu reste alors tel qu'il était, ni réécrit ni désactivé.
- Une lecture en échec ne change rien au compte (rien n'est désactivé parce que la plateforme n'a pas répondu) et le job réessaie ; un compte dont le connecteur ne lit pas de scripts est sauté (`skipped`), un compte qui n'est pas à elle ou d'une créatrice archivée n'est pas lu (`unknown_account`).
- Les tables sont sous la RLS de la créatrice (FORCE), lues par le propriétaire et les managers actifs qui la suivent (sa liste, comme pour son coffre), fermées au compte de la créatrice. `nirvana_app` ne fait que lire ; l'import écrit en rôle de service (`impera_service`, `withAdmin`).

Lectures (`application/platform-script-reads.ts`) : `reads.platformScripts` (l'écran de l'agence et le serveur MCP, propriétaire et managers actifs qui la suivent, `null` pour tout autre lecteur et pour une créatrice inconnue) lues dans la transaction de la personne (`withTenantMember`, la RLS de la créatrice et la portée de l'équipe ; la règle « manager de sa liste » est `onCreatorList` de `@impera/db`, la même que pour ses chiffres), et `forJobs.platformScript` (un script d'elle par son id, hors personne et en rôle de service : pour un job seulement, avec un id que la base lui a donné, jamais un id venu d'une requête ni depuis une route ; ce qu'un job de l'agent lit avant d'envoyer une étape, comme la récompense du jeu des cœurs, ADR 0111). Chaque script porte :

- `warnings` (`priceWarnings`, calculées à la lecture, rien n'est stocké) : une étape payante plus du double de l'étape payante d'avant (`price_more_than_double`), ou au-dessus de 40 € TTC (`price_above_ceiling`, `PLATFORM_SCRIPT_PRICE_CEILING_MINOR`, unité confirmée par Charles le 14/11/2026). Un avertissement, jamais un refus ;
- pour chaque média, sa place dans le coffre (`inVault`, `mediaAssetId`, `described`, par `media_platform_refs` du module `media`) ; une étape dont un média manque au coffre est incomplète (`complete`) ;
- `identity` : l'identité de sa version actuelle (ci-dessous), la dernière validée, sinon la dernière écrite, à valider ; aucune tant qu'aucune n'est écrite pour cette version ;
- `gaps` et `proposable` : un script est proposable à la vente s'il est actif, que chaque média est au coffre, chaque photo et vidéo avec une description validée (une note vocale n'est jamais décrite), que l'identité de sa version actuelle est validée (`identity_not_validated`), qu'aucune de ses étapes n'a de branches (`branched_step`), et qu'aucune ne porte un « Tarif réduit » posé dans Reveal (`step_discounted` ; l'envoi d'une telle étape est aussi refusé par le connecteur, `script_step_discounted`, recette du 16/11). Une récompense offerte ne demande ni description ni identité : elle lit `mediaAssetId`.

`reads.discountedScripts` (mêmes droits que `reads.platformScripts`) donne ses scripts actifs dont une étape porte un « Tarif réduit », sans texte ni média : leur nom, combien d'étapes et depuis quel import (`version_at`, l'import qui a écrit la version actuelle ; un import qui ne change rien ne le bouge pas), le plus ancien d'abord. C'est l'alerte de « bloquer et alerter » (Charles, recette du 16/11) : « À traiter » la montre en ambre tant que l'agence n'a pas retiré la remise dans Reveal.

**Identité d'un script natif** (SC-04 lot c8, ADR 0056 § 6, `domain/script-identity.ts`, table `script_identities`). Ce qu'est le script et quand il tombe juste, pour que le cerveau et les chatteurs choisissent parmi les scripts que le code permet (ADR 0098 § 6) : son ambiance, son énergie (`soft`, `rising`, `intense`), son décor, de une à cinq situations « à utiliser quand » et jusqu'à cinq « à éviter quand » (`ScriptIdentityContentSchema`). Le moment n'y est pas : celui du script (`moment`) l'accompagne à la lecture.

- Elle vaut pour une version du script : son empreinte d'entrée (`identityInputHash`) prend le nom, et pour chaque étape son rang de la plateforme, son nom, son texte et ses médias (vendus et aperçus) avec la description validée de chacun. Jamais un prix : un prix changé garde l'identité. Un texte, un média ou une description validée à nouveau en demande une autre ; celle qui était validée reste, pour sa version, et n'est plus montrée.
- Le job `scripts.identify_platform_script` (`application/identify-platform-script.ts`, un script à la fois, en rôle de service) l'écrit par le cerveau (prompt `brain/script-identity`, sous le plafond du jour) à partir des noms, des textes et du `detailed` de chaque description validée, quand chaque photo et vidéo a sa description validée (aucun interrupteur depuis le 17/11, ADR 0145 § 5). Il ne fait rien pour une version qui en a une validée, écrite à la main, ou écrite par le cerveau avec le prompt du moment ; budget épuisé, il attend le rattrapage ; un cerveau en échec fait échouer le job, qui réessaie. Un script à branches n'est jamais raconté.
- Il est mis en file après chaque import pour les scripts ajoutés ou réécrits, et chaque heure par `scripts.identify_backlog` (`crontab.ts`, à 40) pour chaque script actif d'une créatrice non archivée dont l'interrupteur est allumé, ceux à l'identité la plus ancienne d'abord, au plus 200 : c'est lui qui reprend une description validée depuis, ou un budget épuisé.
- L'agence la valide telle qu'elle est (`POST /v1/creators/:creatorId/platform-scripts/:scriptId/identity/validate`, idempotent ; `script_identity_stale_conflict` si ce n'est pas celle de la version actuelle) ou l'écrit à la main (`…/identity/correct`, validée par qui l'écrit) : le propriétaire et les managers actifs de sa liste, dans leur transaction, sous sa RLS, avec une ligne `script_identity.validated` ou `script_identity.corrected` dans `audit_log`. La liste est `GET /v1/creators/:creatorId/platform-scripts`. Un autre lecteur reçoit le même 404 pour un script qui existe et un qui n'existe pas.
- Avant elle, les descriptions de ses médias : chaque média d'étape (vendu ou aperçu) porte dans la liste la description que l'agence relit (`description` : la dernière avec un `detailed`, une validée d'abord), et l'agence la valide (`POST …/platform-scripts/:scriptId/descriptions/validate`, plusieurs d'un coup, idempotent) ou la récrit (`…/descriptions/correct`, nouvelle ligne `model = 'human'` validée par qui l'écrit, celle de la vision gardée). Une description qui n'est plus celle montrée est refusée (`platform_script_description_stale_conflict`), et une description à vérifier (`reviewReasons` non vide) ne part jamais dans un lot (`platform_script_description_alone_conflict`) : elle se valide seule, après lecture. Mêmes droits, même transaction et même 404 que l'identité, avec `media_description.validated` ou `media_description.corrected` dans `audit_log`, puis le job d'identité mis en file pour le script. L'écran est la carte « Ses scripts dans Reveal » de Créatrices › Scripts.
- Une ligne s'écrit une fois puis se valide une fois (déclencheur `script_identities_kept`, comme les descriptions) ; `nirvana_app` ne peut que lire, écrire une identité humaine qu'il valide lui-même et poser le tampon ; fermée au compte de la créatrice.

**Étape à branches** (ADR 0112, en préparation). Deux étapes d'une séquence Reveal au même rang (`stepIndex`) sont des branches entre lesquelles une personne choisit. L'import les garde côte à côte, chacune à sa place (`position`) avec le rang de la plateforme (`platform_index`), sans les interpréter ; un tel script n'est jamais proposable ni raconté au cerveau tant que le modèle à branches n'existe pas. La condition d'une branche sera gardée quand un enregistrement réel montrera son champ.

La plateforme est lue par `connectors` (`platformReads.scripts`, donné par le composition root comme `platformScripts.source`) : pas de session utilisable ou pas de lecture des scripts, le compte est sauté ; une plateforme qui ne répond pas fait échouer le job, qui réessaie. Les liaisons du coffre sont lues dans `media_platform_refs` (synchronisation du coffre), dans la même transaction que les scripts (`infra/db/platform-script-store.ts` : celle de la personne pour `reads`, le rôle de service pour `forJobs` ; `forJobs.accountScripts` donne à l'agent les scripts d'un compte, avec `proposable` et `ours`, le script préparé dont chacun est la copie reconnue, avec notre description, notre moment et nos prix par étape et par branche, ou `null` : seuls ceux-là peuvent être offerts, ADR 0161 § 5), bornées par le compte : une liaison retirée (`removed_at`) n'est plus au coffre ; `described` dit qu'une description de son média a été validée par une personne.

**Scripts en préparation** (ADR 0112 §§ 20-22, amendement du 19/11). Un script écrit dans l'éditeur d'Impera, qui n'existe pas encore chez Reveal, est gardé dans `prepared_scripts` : son contenu (`PreparedScriptContentSchema`), son état (`editing`, `ready_to_copy`, `matched`) et sa révision. Il n'est jamais proposé ni envoyé ; Impera n'écrit rien chez Reveal, une personne le recopie à la main.

- `GET /v1/creators/:creatorId/prepared-scripts` et `…/:scriptId` : le propriétaire et les managers actifs de sa liste, dans leur transaction, sous sa RLS ; un chatteur de sa liste reçoit le même 404 pour un script qui existe et un qui n'existe pas, le compte de la créatrice et le manager d'une autre un 403.
- `POST …/prepared-scripts` sous l'identifiant du client : le même envoi est rejoué (200), un autre contenu sur cet identifiant est refusé (`prepared_script_conflict`), un compte qui n'est pas le sien aussi (`prepared_script_account_invalid`).
- `PUT …/:scriptId` enregistre sur `basedOnRevision` (`prepared_script_stale_conflict` sinon) et remet un script « prêt à copier » en préparation ; `POST …/:scriptId/ready` le rend « prêt à copier » seulement sans manque (`prepared_script_gaps_unprocessable`), `…/editing` le remet en préparation. Un script reconnu par un import (`matched`) est fermé (`prepared_script_closed_conflict`).
- Les manques (`preparedScriptGaps`) et les avertissements de prix sont comptés à chaque lecture, jamais gardés : un média décrit depuis, ou une persona changée, les change sans enregistrement. Ils reprennent les refus des branches (`branchGaps`) et lisent son coffre dans `media_platform_refs` comme les scripts natifs.
- Chaque écriture ajoute `prepared_script.created`, `.saved` ou `.state_changed` dans `audit_log`.
- **Reconnaissance** (§ 23, `domain/recognition.ts`, `infra/db/recognition-store.ts`) : après chaque import des scripts natifs, dans une transaction du rôle de service, chaque script « prêt à copier » du compte (le plus ancien d'abord) est rattaché au premier script natif actif qui lui correspond en tout (même nom, même nombre d'étapes, même nombre de branches à chaque rang, chaque branche aux mêmes médias vendus et au même prix ; les textes ne sont pas comparés), à condition qu'aucun autre ne l'ait pris et que l'agence n'y ait réglé aucune branche. L'ordre et les conditions de ses étapes à plusieurs branches passent dans `platform_script_branches` (une condition « branche précédente » par le `stepRef` de Reveal), sous la personne qui l'a rendu prêt ; le script en préparation passe `matched`, avec une ligne `prepared_script.matched` (sans personne). Le teaser, les messages après le média et le rythme restent lisibles sur le script fermé jusqu'à ce que le déroulé à branches les lise. Tant qu'il n'est pas reconnu, la lecture donne `copyDifferences` : ce qui diffère du script natif du même nom le plus proche, ou `name_not_found`.

Chaque écriture ajoute une ligne `script_structure.create`, `.update`, `.archive`, `.freeze` (sans compte quand le job fige), `script_queue.update` ou `script_cadence.update` dans `audit_log`.

## Structure

- `domain/` : limites de la persona, décision d'enregistrement, vue de la file, cartons, ports `ScriptStructureStore` et `RasterizeCard`. Zéro I/O.
- `domain/platform-scripts.ts` : le plan d'import des scripts natifs, leur empreinte, les avertissements de prix et ce qui les empêche d'être proposables. Zéro I/O.
- `domain/script-identity.ts` : l'empreinte d'entrée de l'identité, quand le cerveau peut l'écrire, les branches, l'identité de la version actuelle. Zéro I/O.
- `application/` : le job de la cadence, l'import des scripts natifs et leur lecture, et la lecture de sa file par l'agence (`reads.ts`), pour la route et le serveur MCP (ADR 0026 § 1) : `reads.queue` de `index.ts` rend, bornée par son id et le lecteur vérifié, chaque structure de sa file par son nom, son moment et le nombre de ses étapes et ponts, jamais le texte d'une étape ; `null` pour un lecteur qui ne lit pas sa file.
- `infra/db/` : les tables, chaque ligne relue par le contrat.
- `domain/prepared-scripts.ts` : ce qui manque à un script en préparation, ses avertissements de prix, ses états. Zéro I/O.
- `domain/recognition.ts` : la correspondance exacte d'un script recopié, les réglages transmis, ce qui diffère. Zéro I/O.
- `infra/http/` : les routes (`platform-script-routes.ts` pour les scripts natifs et leur identité, `prepared-routes.ts` pour les scripts en préparation).
- `infra/script-identifier.ts` : le cerveau de la passerelle pour l'identité.
- `infra/card-rasterizer.ts` et `infra/fonts/` : le PNG d'un carton.
